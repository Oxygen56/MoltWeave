# v0.2：机制变更如何进入后续真实执行

原始执行文件通过完整证据包分发，以下 raw 路径需先解压到新克隆的仓库，再在本地查看；GitHub 网页只保存紧凑报告与解释性索引。
这份材料确认了三条 M 变更确实影响后续宿主决策的链路，也保留了新机制之后的失败。它不证明总体效果提升：检查时正式演化在 provider 再次 HTTP 402 后停于 **501/600 个已提交轮次**，最终独立验收尚未完成。本材料属于 preview 的解释性证据，不是 stable 发布或效果结论。

本材料的路径和 SHA256 绑定 `v0.2.0-preview.1` 的 501 轮证据快照；后续续跑可能更新工作目录的 summary，核验时应使用这份历史快照。

完整机器可读材料见 [v02-mechanism-witnesses.json](verification/v02-mechanism-witnesses.json)。其中保存三个案例的字段前后值、实际 features、事件与任务结果，以及 41 个引用文件的原始字节 SHA256；冻结九份核心源码也逐一与 manifest 的 source digest 核对。两种 hash 的计算口径在 JSON 中分别注明。检查没有调用模型、修改核心源码或改写正式回执。

## 先看共同链路

每轮先用当前 M 执行任务，再由真实模型提出受限 IR 或 prompt 变更。固定宿主验证和执行候选，通过开发筛选的 M 写入下一代 checkpoint；下一轮读取该 checkpoint 的 M，重新计算记忆写入门、记忆排序和 RAG 排序。模型不能改写来源校验、租户边界、评分器或这套执行程序。

下面每个案例都逐项核对：`mechanism-search.json` 中已执行、被采用的候选 → `transition.loaded_m_next` → 下一代 checkpoint 的 M hash → 下一轮 `experience.mechanism_hash`、任务请求和实际事件中的同一 hash。下一轮还必须有自己的提交 checkpoint，避免把中断中的 partial 当成正式结果。真实提案和任务的 provider 原始回执也纳入 SHA256 引用。

旧 IR 对照是 **deterministic post-hoc diagnostic（确定性的事后诊断）**：保持实际记录的候选池及 features 不变，仅用冻结解释器代入旧 IR，比较分数和宿主选择。它没有再请求模型、没有重建完整旧 M 轨迹，也没有测量旧 M 会给出什么答案。案例由事后扫描挑选，用于说明机制如何工作，不能估计收益或发生频率。

环境是项目公开编写的合成事件流，回答来自真实 provider 模型；不是企业数据或原生外部 benchmark。`V…` 注册值属于合成任务值，不是 API 凭据。任务的正确答案只在真实输出和写入封存后用于评分及本次解释，没有进入模型的事实提取输入。

## 1. 写入规则改变了真实提议的处理结果，但后续仍有失败

**101 / joint / r04 → r05**。r04 采用的 M 改了 `memory_write` 和 `rag_score`，下一轮实际加载的 M hash 为 `770ac88c94ff…`。来源可从 [r04 transition](../experiments/continual-v02-main/streams/101/joint/rounds/r04/transition.json)、[g5 checkpoint](../experiments/continual-v02-main/streams/101/joint/versions/g5.json) 和 [r05 experience](../experiments/continual-v02-main/streams/101/joint/rounds/r05/experience.json) 追踪。

在 r05 第一个任务中，真实 writer 提议保存一条 replica 事实 `src-b80cb142026fed13a3`。宿主确认它逐字段来自当前可见、trusted 的来源，然后算出 `verified=1, duplicate=0, conflict=1, is_newer=1, source_match=0`。旧规则会因为 `is_newer=1` 通过写入门，分数是 **1**；新规则对这个冲突 replica 算出 **0**，实际产生 `rejected / memory_write_nonpositive`，事件 ID 为 `event-00000099`。

同次 ingest 对 primary 事实算出 **1**，实际产生 `replaced / newer_same_source_family`，保留被替代记录的来源链。这里直接证明了新写入规则参与真实执行，而不是只改了配置文件。对照只声称“旧写入门会通过”，不越过固定宿主的撤回、同源修订和来源校验等后续约束。

失败也保留：r05 只有 **3/6** 个任务通过；第一次 recall 成功，纠正后的第二次 recall 仍回答旧值，另两个保留任务也失败。此外，r04 初始联合提案未满足“两个选中模块实际都变化”的约束，被宿主拒绝；一次真实修复调用后才产生被采用的变更。JSON 同时引用原提案、修复回执和验证错误，没有把首次提案写成直接成功。

## 2. 排序公式改变了所读记忆，也暴露了坏策略

**104 / joint / r01 → r02**。r01 给 `memory_score` 加入 `1.5 × revision`，同时修改 prompt；`memory_top_k` 仍是 **3**。下一轮加载 M hash 为 `ba4161050960…`。来源见 [r01 transition](../experiments/continual-v02-main/streams/104/joint/rounds/r01/transition.json)、[g2 checkpoint](../experiments/continual-v02-main/streams/104/joint/versions/g2.json) 和 [r02 experience](../experiments/continual-v02-main/streams/104/joint/rounds/r02/experience.json)。

r02 第一个 recall 查询当前实体 `Entity-2c1e4b656f`。其 primary 记忆 `memory-0009e45b86b9aa36aee71572` 在同一实际 features 上，旧分数为 **18.9091**、新分数为 **20.4091**。但同实体的邻居干扰记录 revision 为 30，新分数升到 **61.7273**；另一实体的邻居记录升到 **60.6287**，当前实体 replica 升到 **47.5091**。这三条成为实际读出的 top 3，当前实体 primary 被挤出。

按旧 IR 在同一候选池排序，当前 primary 会排第一并进入 top 3。JSON 保存全部八条候选的实际 features、旧／新分数、原始插入顺序和选中 ID；新排序与 `read_completed` 事件及发给真实任务模型的 `selected_memories` 一致。由于 top-k 没变，这里的选择差异可以定位到评分公式，而不是上下文数量扩张。

这条策略将不同来源的局部 revision 直接加到一个全局分数，放大了高 revision 干扰。它改变了决策，却不是值得宣传的改进：该 recall 实际返回 `UNKNOWN`，r02 全轮 **0/5**。prompt 也同时变化，所以不能把模型答案的失败单独归因于评分公式；本例严格证明的是“新排序确实将当前 primary 挤出实际输入”。

## 3. RAG 变更让策略事实进入真实请求，单项功劳仍需拆开

**103 / joint / r06 → r07**。r06 给 `rag_score` 加入 `6 × (1 − key_match)`，并将 `rag_top_k` 从 **3** 改为 **5**；其他 M 字段没有变化。下一轮加载 M hash 为 `4383a49188bf…`。来源见 [r06 transition](../experiments/continual-v02-main/streams/103/joint/rounds/r06/transition.json)、[g7 checkpoint](../experiments/continual-v02-main/streams/103/joint/versions/g7.json) 和 [r07 experience](../experiments/continual-v02-main/streams/103/joint/rounds/r07/experience.json)。

r07 第一个任务需要同时看到 governing policy 和该 policy 指定的 replica token。策略事实 `src-084cac2a103b53f3d5` 的 key 是 `source_of_truth`，与查询的 `registration_token` 不同。对这份真实文档，旧分数 **15.9130**、新分数 **21.9130**，排名由第五升到第二；新 top 5 也保留了指定 replica 的 token。两条来源确实出现在真实模型请求中，模型返回 token 并同时引用两条来源，封存后评分通过。

离线拆分显示：仅换新评分、仍取 top 3，policy 会进入但指定 replica 会被截掉；仅扩为 top 5、仍用旧评分，也能容纳这五份文档中的 policy 和 token。因此，本例能证明“这次真实 RAG 变更改变了可见证据，并出现一次有正确双引用的回答”，不能把收益单独记给评分项，更不能宣称它优于单纯扩大上下文。也没有向旧 M 再发请求来测量反事实答案。

失败仍在：紧接着的第一次纯记忆 recall 返回 `UNKNOWN`，保留任务也失败，r07 为 **4/6**。检索时把 policy 提供给模型，没有自动解决其后持久记忆的写入和召回。

## 可使用的表述边界

可以说：**正式回执证明了自动产生、实际采用的 M 变更进入后续轮次，并改变真实写入门、记忆选择或 RAG 输入；其中也有明确的失败策略。**

不能据此说 v0.2 总体提升、跨任务泛化提升、P 已有独立收益，或已通过最终验收。相邻轮次的任务与状态不同，不能把这里的 3/6、0/5、4/6 当成新旧 M 的配对效果；旧 IR 诊断也不能替代冻结版本的独立读出。
