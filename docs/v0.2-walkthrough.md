# 一条真实执行链怎么读

原始执行文件通过完整证据包分发，以下 raw 路径需先解压到新克隆的仓库，再在本地查看；GitHub 网页只保存紧凑报告与解释性索引。
这份讲解对应 v0.2 正式运行中已封存的执行记录。它证明机制和 P 后代确实运行，不代表正式独立收益已经成立。示例是为方便理解而选出的成功链；全量失败与退化记录保留在同一证据包中，不能用示例替代总体成功率。

## 先看长期记忆

一条基本事件序列有四步：Agent 从授权来源观察事实，由独立模型调用提出记忆，固定外层核验字段和来源后让 M 的写入程序决定是否保留；下一步移除文档和工具，仅靠已写记忆回忆；随后来源发布更高版本的新事实；最后再次移除外部输入，检查 Agent 是否读取新记录并给出新答案。

证据需要连到具体 ID：第一次写入的 record ID 出现在第二步实际读取中；第三步替换事件指向该旧 ID 和新 ID，且属于同一来源修订链；第四步实际读取新 ID。单有四个正确答案、一次向量检索或一份生成的“反思”，都不能替代这条链。

[执行证据索引](verification/v02-execution-witnesses.json)从三个实验臂各保留一条实际成功链，绑定原始文件字节的 SHA256。正式序列另有跨轮和三轮延迟回忆，既看新更正能否生效，也看旧的有用事实是否仍能取回。不同来源的版本号不可直接比较，租户和 owner 过滤始终先于演化评分。

## 再看“改进方法”是否真的递归

正式 stream 102 的 joint 臂已经保留了三个 P 后代的采用与下一轮实际加载：

| 在哪个轮次后采用 | 新 P 哈希前缀 | 成对未来搜索的开发读数：旧 P → 新 P | 下一轮实际使用新 P 做了什么 |
|---|---|---|---|
| r02 | `df580236200c` | 0/4 → 2/4，保护任务均 2/2 | 选择 memory+RAG、memory+prompt+RAG 的联合修改，并从已执行但未采用的父候选出发 |
| r05 | `ea50157a1670` | 3/4 → 4/4，保护任务均 2/2 | 转向 memory 重写，分别选择 current 与 best_rejected 父候选 |
| r07 | `f00290a5e98d` | 0/4 → 1/4，保护任务均 2/2 | 选择 recovery 重写，实际生成并测量后续候选 |

每一行都绑定原始 transition、成对探测和下一轮 mechanism-search；下一轮记录的 policy_hash 与采用的新 P 完全一致。r02、r05、r07 指从零开始的轮次编号。这是一条“新 P 运行→产生新搜索历史→再产生新 P”的真实链，而不是只把版本名从 P1 改成 P2。

这些未来搜索属于反复使用的 **meta-development 优化数据**。门槛只说明当时的候选值得前瞻采用。新 P 后续也可能选择错误解释、无效修改或产生退化。因此上表不能证明 P 在独立任务上优于固定 P，更不能把三个正向门槛读数相加当成总体提升。

## 最后看正式验收

全部预定版本冻结后，各代 M 从空记忆执行同一新事件序列，避免仅因携带更多已知答案而占优；末代再禁用记忆、扩大固定基线上下文。P 验收则重新让 P0 与各检查点 P 从同一状态执行未来搜索：固定基线 M、fixed-P 臂末代记忆与搜索历史，以及同一份新的观察记录。审计只提供 current 父候选；它检验 P 到共同搜索状态的迁移，不是继续运行联合臂的末代 M。g0 的 P0/P0 对照暴露同策略模型采样波动，非法搜索和无效配对单列。

目前正式执行因模型服务余额不足而中断，尚未完成这项独立验收。公开文档将该结果记为 unavailable，不从开发示例推导效果，也不删掉失败的候选来补出一条好看的曲线。
